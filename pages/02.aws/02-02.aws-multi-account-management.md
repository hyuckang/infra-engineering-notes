## Account
- **`Account(계정)`는 AWS 리소스를 생성하고 관리하는 기본 단위인 Resource Container**로 EC2, S3 등 AWS 리소스를 담는 논리적인 컨테이너입니다. 각 Account는 다른 Account와 구별되는 고유한 12자리 식별자(`Account ID`)를 가집니다. 
- **Account는 리소스, 보안, 접근 권한, 비용에 대한 논리적인 경계(Isolation Boundary)를 제공**하고, Account 간의 리소스는 기본적으로 격리되어 명시적인 권한 없이는 접근할 수 없습니다.
- **`Root User`는 Account 생성 시 등록한 이메일 주소와 연결된 최상위 권한의 사용자**입니다. Account 내 모든 AWS 서비스와 리소스에 대한 접근 권한을 가지며, 보안을 위해 일반적인 운영 및 관리 작업에 사용하지 않고 Root 권한이 반드시 필요한 작업에만 사용하는 것이 권장됩니다.
- `Service Quotas`는 AWS 서비스별로 생성하거나 사용할 수 있는 최대 수량을 제한하는 할당량으로, 일반적으로 Account와 Region 단위로 적용되므로 Account를 분리하면 워크로드 간 할당량 경합을 방지할 수 있습니다.
- **AWS는 Multi-Account Architecture를 모범 사례로 권장합니다.** 워크로드 및 환경(개발/상용)별로 Account를 분리하여 보안 사고 및 장애의 영향 범위(Blast Radius)를 최소화하고, **Organizations를 통해 여러 Account를 중앙에서 일관되게 관리하는 것을 권장**합니다.

## Organizations
- `Organizations`는 여러 AWS Account를 하나의 조직(Organization)으로 통합하여 중앙에서 관리하는 서비스입니다.
- Organization에 소속된 Account는 `Management Account`와 `Member Account`로 구분됩니다.
- **Management Account는 AWS Organizations를 생성하고 조직 전체를 관리하는 Account**입니다. 조직의 최상위 관리 권한을 가지며, 계정, 조직 정책, 서비스 통합 및 결제 등을 중앙에서 관리합니다. 또한 `Payer Account` 역할을 수행하여 조직 내 모든 Account에서 발생한 비용을 통합 청구 결제합니다.
- `Member account`는 Management Account를 제외한 Organization에 소속된 모든 AWS Account입니다. 하나의 Account는 하나의 Organization에만 소속될 수 있습니다.
- `Organization Root`는 Organizations 생성 시 자동으로 생성되는 최상위 컨테이너로, 모든 OU와 Account가 Organization Root에 속하게됩니다. Root에 적용된 조직 정책(Organizations Policies)은 하위 OU와 Member Account에 상속됩니다.
- Organization Root는 조직의 계층 구조를 관리하는 논리적 컨테이너로, AWS Account의 최상위 권한을 가진 Root User와는 다른 개념입니다.
- Account Management는 AWS Organizations를 통해 Member Account를 생성하거나 기존 AWS Account를 조직에 초대하고, 계정의 이동, 폐쇄 등을 중앙에서 관리할 수 있는 기능입니다.
- **`Organizational Unit(OU)`는 Organizations에서 여러 Account를 논리적으로 그룹화하여 하나의 단위로 관리하기 위한 Organization 구성 요소**입니다.
- OU는 하위 OU를 포함하는 계층 구조로 구성할 수 있으며, 상위 OU에 적용된 조직 정책은 하위 OU와 Account에 상속됩니다.
- **`Delegated Administrator`는 Management Account가 AWS 서비스(Organizations, SecurityHub, GuardDuty 등)의 조직 단위 관리 권한을 Member Account에 위임하는 기능**으로 Management Account의 직접적인 사용을 최소화하고 관리 권한과 책임을 분산할 수 있습니다.

### Organizations Policies (Authorization policies와 Declarative policies)
- **`Organizations Policies(조직 정책)`는 멀티 계정 환경에서 AWS 계정의 권한을 제한하거나, AWS 서비스의 설정과 운영 정책을 중앙에서 관리하기 위한 기능**입니다
- Organizations Policies는 크게 `Authorization policies`와 `Declarative policies`로 구분됩니다.
- **`Authorization Policies`는 조직 내 Account의 IAM Principal과 AWS 리소스에 대한 최대 접근 권한을 제한하는 정책**으로, `Service Control Policy(SCP)`와 `Resource Control Policy(RCP)`로 구분됩니다. SCP는 IAM User, Role 등 Principal이 수행할 수 있는 작업을 제한하고, RCP는 리소스에 대한 접근을 제한합니다. SCP와 RCP는 권한을 직접 부여하지 않습니다.
- **`Declarative Policies`는 AWS 서비스의 구성과 운영 기준을 조직 단위로 선언하고 중앙에서 관리하는 정책**으로, 지원되는 서비스의 설정을 강제하거나 백업 계획, 태그 표준 등의 운영 정책을 일관되게 적용할 수 있습니다.

### Account & Organizations Best Practices
- **Management Account에는 SCP와 RCP가 적용되지 않습니다. 따라서 접근 권한을 최소한의 관리자에게만 부여하고, Management Account에서만 수행할 수 있는 조직, 계정, 결제 등의 관리 작업에 한정하여 사용하는 것이 권장됩니다.**
- Management Account에는 일반적인 비즈니스 워크로드를 실행하지 않고, Organizations 관리에 필요한 리소스만 유지하는 것을 권장합니다.
- AWS Organizations에서는 Member Account의 Root 자격 증명을 중앙에서 관리하고 제거하는 것을 권장하며, 이를 통해 Root User의 직접적인 로그인을 제한하고 계정 보안을 강화할 수 있습니다.
- AWS Account의 Root User 이메일 주소는 개인 이메일이 아닌 회사에서 관리하는 그룹 이메일 주소를 사용하여, 특정 담당자의 부재나 퇴사로 인해 계정 접근 및 복구가 어려워지는 것을 방지해야 합니다.
- AWS Account에 대한 **사용자 접근은 IAM User 대신 IAM Identity Center 등의 연동 인증(Federated Access)을 통해 통합 관리하는 것이 권장**되며, 이를 통해 Account별 사용자 관리 부담을 줄이고 접근 권한을 일관되게 관리할 수 있습니다.
- Management Account의 접근 권한과 Root User에 연결된 이메일, MFA, 전화번호 등의 복구 수단을 최소 월별 또는 분기별로 검토하여, 필요한 관리자만 접근할 수 있도록 유지하는 것이 권장됩니다.
- **워크로드 및 환경(상용, 개발, 테스트)별로 Account를 분리하는 멀티 계정 아키텍처를 권장**하며, 이를 통해 보안 사고, 잘못된 설정, 장애의 영향 범위를 최소화할 수 있습니다
- AWS Account는 용도, 워크로드, 환경을 식별할 수 있도록 이름과 이메일 주소의 명명 규칙을 표준화하고, 계정 태그를 활용해 관리 목적과 비용 귀속을 명확히 하는 것이 권장됩니다.

## Control Tower
- `Control Tower`는 모범 사례를 따르면서 Multi Account 환경을 간편하게 설정하고 관리할 수 있는 방법을 제공합니다.
- Control Tower는 AWS의 보안 모범사례를 기반으로 NIST 800-53, PCI-DSS 등의 규정 준수 프레임워크에 따라 Control를 분류하고 관리할 수 있도록 지원합니다. 이를 통해 조직의 보안 요구사항에 적합한 Control를 선택적으로 적용하고, AWS Multi Account 환경에서 일관된 보안 정책과 위험 관리 체계를 구축할 수 있습니다.
- `Landing Zone`은 AWS의 보안, 운영 모범 사례를 기반으로 Account 구조, 접근 관리, 로깅 등의 공통 구성을 갖춘 표준화된 멀티 계정 환경으로, AWS Control Tower를 통해 자동으로 구성하고 관리할 수 있습니다.
- `Account Factory`는 사전에 정의한 표준 구성을 기반으로 새로운 AWS Account를 자동으로 생성하고 프로비저닝하는 기능으로, 조직 내 계정을 일관된 구성으로 관리할 수 있습니다.
- `Baseline`은 AWS Control Tower에서 계정의 보안, 감사, 운영에 필요한 AWS 리소스와 설정을 정의한 집합입니다. OU 등에 적용하여 대상 Account에 IAM Role, AWS Config 등의 리소스와 설정을 자동으로 배포하고 관리합니다.
- `Drift Detection`은 AWS Control Tower에서 관리하는 Landing Zone, Baseline, Control 등의 표준 구성과 실제 환경 간의 불일치를 자동으로 탐지하는 기능으로, 조직의 거버넌스 기준에서 벗어난 변경 사항을 식별하고 관리자에게 알림을 제공합니다.

### Control Tower Controls 유형
- AWS Control Tower의 **`Control`은 Multi Account 환경에서 보안 정책과 규정 준수를 관리하기 위한 통제 기능**입니다. Control은 OU 단위로 적용되며 동작 방식에 따라 `Preventive`, `Detective`, `Proactive`로 구분되고, 적용 권장 수준에 따라 `Mandatory`, `Strongly recommended`, `Elective`로 분류됩니다.
- `Preventive control`는 Organizations의 SCP, RCP, Declarative policies를 사용하여 구현됩니다. 조직의 보안 정책에 위배되는 AWS 작업을 사전에 차단하거나 특정 리소스 구성을 강제합니다.
- `Detective control`는 Config Rules를 사용하여 구현됩니다. AWS 리소스의 구성 상태를 평가하여 보안 정책과 규정 준수 여부를 탐지하지만, 위반 작업을 직접 차단하거나 자동으로 수정하지는 않습니다.
- `Proactive control`는 CloudFormation Hooks를 사용하여 구현됩니다. CloudFormation을 통한 리소스 프로비저닝 과정에서 정책 위반을 사전에 검증하고 배포를 차단하지만, CloudFormation을 거치지 않는 리소스 생성에는 적용되지 않습니다.
- `Mandatory Control`은 Control Tower의 핵심 리소스와 거버넌스 구성을 보호하기 위한 필수 통제로, 활성화된 경우 관리자가 임의로 비활성화할 수 없으며 Landing Zone 버전에 따라 기본 적용 여부가 달라집니다.
- `Custom control`는 Control Tower에서 제공하는 Control로 충족하지 못하는 조직의 규정 준수 요구사항을 구현하기 위해 사용자가 직접 정의하는 통제 규칙입니다. SCP, Config Rules, CloudFormation Hooks 등을 활용하여 Control Tower 외부에서 별도로 구현하고 관리할 수 있습니다.
- `Strongly Recommended Controls`는 AWS Well-Architected 모범 사례를 기반으로 멀티 계정 환경의 보안, 운영 수준을 강화하기 위해 권장되는 통제 규칙입니다. 관리자가 조직의 요구사항에 따라 선택적으로 활성화하거나 비활성화할 수 있습니다.
- `Elective Controls`는 조직별 보안, 운영, 규정 준수 요구사항에 따라 추가로 적용할 수 있는 통제 규칙입니다. 특정 작업을 제한하거나 리소스의 규정 준수 여부를 확인하기 위해 선택적으로 활성화할 수 있습니다

### Control Tower Best Practices
- AWS Control Tower에서 생성하고 관리하는 리소스(IAM Role, AWS Config, CloudFormation StackSets 등)는 임의로 수정하거나 삭제하지 않는 것이 권장됩니다. 이러한 변경은 Drift를 발생시키거나 Control Tower의 정상적인 동작 및 규정 준수 평가에 영향을 줄 수 있습니다.
- Control Tower가 생성한 Security OU와 공통 보안 계정(Log Archive, Audit)은 임의로 삭제하거나 다른 OU로 이동하지 않아야 합니다. 이러한 변경은 Landing Zone의 거버넌스 구성을 손상시키고 Drift를 발생시킬 수 있습니다.
- 신규 AWS Account는 Account Factory를 통해 표준화된 구성으로 프로비저닝하는 것이 권장됩니다. 이를 통해 Account 생성 시 필요한 Baseline과 Control을 일관되게 적용할 수 있습니다.
- Region에 대한 접근 제한은 임의의 SCP나 AWS STS 비활성화 대신 Control Tower에서 제공하는 Region Deny Control을 활용하는 것이 권장됩니다.
- AWS는 Root 사용자에 대한 보안 위험을 최소화하기 위해 AWS-GR_RESTRICT_ROOT_USER_ACCESS_KEYS(Root 사용자의 Access Key 생성 금지), AWS-GR_RESTRICT_ROOT_USER(Root 사용자 자격 증명을 사용한 AWS API 작업 금지) 2가지의 Strongly Recommended Controls를 적용할 것을 권장합니다.
