# 01-1. Cloud Native
## CNCF(Cloud Native Computing Foundation) 
`CNCF`란 Linux Foundation 산하에 설립된 비영리 재단으로, 클라우드 네이티브 기술과 오픈소스 생태계를 관리하고 육성합니다.

## Cloud Native
- `Cloud Native`는 **클라우드 컴퓨팅의 이점을 최대한 활용하기 위해 확장성(Scalability), 회복성(Resilience), 관리 용이성(Manageability), 관측 가능성(Observability), 자동화(Automation) 등을 중심으로 애플리케이션과 인프라를 설계·구축·운영하는 접근 방식**입니다.
- 기존에는 애플리케이션과 인프라가 특정 환경에 종속되고 수동으로 관리되어, 시스템 확장과 장애 복구가 어렵고 운영 부담이 증가하는 문제가 있었습니다.
- Container, Service Mesh, Microservices, Immutable Infrastructure, Declarative API 등이 대표적인 기술 및 설계 방식이며, 이를 활용하여 느슨하게 결합된(Loosely Coupled) 시스템을 구축하고, 배포·확장·복구를 자동화하여 유연하고 안정적인 운영을 지원합니다.

## DevOps
- `DevOps`는 **애플리케이션의 개발부터 운영까지 전체 생명주기를 하나의 팀이 책임지는(End-to-End Ownership) 방법론**입니다. 단순히 기술을 도입하는 것을 넘어 조직 문화와 업무 프로세스의 근본적인 변화(Culture & Process Change)를 요구합니다.
- 전통적으로 애플리케이션 개발과 운영 업무는 여러 팀에 분산되어 있었으며, 작업이 완료될 때마다 다음 팀으로 전달되는 방식이었습니다. 이로 인해 전체 결과에 대한 책임 의식이 약해지고, 고객에게 필요한 기능을 제공하기보다 다음 팀에 작업을 전달하는 것이 목표가 되는 문제가 발생했습니다.
- DevOps는 **팀 간 업무 인계(Handoff)를 최소화하고 개발부터 운영까지 전체 생명주기에 대한 책임을 강화하여, 소프트웨어를 더 빠르고 안정적으로 배포·운영할 수 있도록 합니다.**

## DevSecOps
- `DevSecOps`는 **DevOps에 보안(Security)을 통합하여 개발·운영·보안이 애플리케이션의 전체 생명주기에 대한 책임을 공유하는 조직 문화이자 업무 방식**입니다. **개발 및 운영 프로세스의 흐름을 최대한 방해하지 않으면서 보안을 통합하는 것을 목표**로 합니다.
- 전통적으로 보안은 개발 및 운영과 분리되어 관리되는 경우가 많았으며, DevOps를 통한 개발·배포 주기의 가속화로 보안 요구사항이 충분히 고려되지 않은 소프트웨어가 빠르게 배포되어 보안 위험이 증가하는 문제가 발생할 수 있었습니다.

## Shift Left
- `Shift Left`는 **소프트웨어 개발 생명주기(SDLC) 테스트·보안 검증 등의 활동을 개발 초기 단계로 앞당기는 접근 방식**입니다. 개발 과정을 왼쪽에서 오른쪽으로 진행되는 흐름으로 표현했을 때, 검증 활동을 왼쪽(Left)으로 이동(Shift)한다는 의미입니다.
- 전통적인 개발 방식에서는 테스트와 보안 검증이 개발 후반부에 집중되는 경우가 많았으며, **개발 후반부나 운영 환경에서 결함 또는 보안 취약점이 발견되면 수정에 더 많은 시간과 비용이 발생하는 문제가 있었습니다.**
- Shift Left는 설계·개발 초기 단계부터 테스트와 보안 검증을 수행하고 개발팀 전체가 품질과 보안에 대한 책임을 공유하여, 문제를 조기에 발견·수정하고 소프트웨어의 안정성과 보안성을 높일 수 있도록 합니다.

## Container와 Containerization
- `Container`는 **운영체제(OS) 수준에서 격리된 환경을 제공하고, CPU·메모리 등의 리소스 사용을 제한하여 애플리케이션을 실행하는 프로세스**이고, `Containerization`는 **애플리케이션 코드와 실행에 필요한 라이브러리·의존성을 하나의 경량 실행 파일로 패키징하는 과정**입니다. 이렇게 생성된 패키지를 `Container Image`라고 합니다.
- Container라는 명칭은 화물 컨테이너처럼 애플리케이션과 실행 환경을 표준화된 형태로 패키징하여, **서로 다른 환경에서도 일관되게 실행**할 수 있다는 개념에서 유래했습니다.
- 기존에는 애플리케이션마다 별도의 서버나 가상 머신(VM)을 사용하는 경우가 많아 운영체제 실행에 필요한 CPU·메모리·스토리지 등의 자원이 중복으로 소모되었으나, Container는 호스트 운영체제의 커널을 공유하여 리소스 사용을 최소화하고, 하나의 서버에서 여러 애플리케이션을 효율적으로 실행할 수 있습니다.

## Container Orchestration
- `Container Orchestration`은 컨테이너화된 애플리케이션의 배포(Deployment), 확장(Scaling), 자동 복구(Self-healing), 모니터링(Monitoring) 등 컨테이너의 생명주기를 자동으로 관리하는 기술입니다.
- Orchestration은 여러 작업을 조율한다는 의미로 대표적으로 Kubernetes, Amazon ECS 등이 Container Orchestration 도구에 해당됩니다.

## Sidecar Container
- `Sidecar Container`란 주 애플리케이션(Main Container)과 함께 실행되며 생명주기를 공유하면서, 별도의 보조 기능을 제공하는 컨테이너입니다.
- 기존에는 로깅(Logging), 모니터링(Monitoring), 트레이싱(Tracing) 등의 기능을 애플리케이션 코드에 직접 구현해야 했기 때문에, 애플리케이션마다 구현 방식이 달라지고 유지보수 및 운영이 복잡해지는 문제가 있었습니다.
- Sidecar Container를 사용하면 주 애플리케이션의 코드를 변경하지 않고도 별도의 컨테이너에서 공통 기능을 제공할 수 있어, 관심사를 분리(Separation of Concerns)하고 운영 및 유지보수를 단순화할 수 있습니다.

## CI/CD
- `CI/CD(Continuous Integration / Continuous Delivery 또는 Continuous Deployment)`는 **코드 변경 사항의 통합·검증·배포 과정을 자동화하여 소프트웨어를 빠르고 안정적으로 제공하기 위한 개발·운영 방식**입니다.
- 기존에는 코드 통합·테스트·배포를 수동으로 수행하면서 코드 충돌과 배포 오류 등이 발생했으나, CI/CD를 통해 이러한 과정을 자동화하여 오류를 조기에 발견하고 소프트웨어를 빠르고 안정적으로 배포할 수 있습니다.
- `CI(Continuous Integration)`란 개발자가 코드 변경 사항을 VCS(Version Control System)에 자주 통합하고, 빌드·테스트·코드 품질 검사를 자동으로 수행하여 오류를 조기에 발견하는 방식입니다.
- `CD (Continuous Delivery)`란 CI를 통해 검증된 소프트웨어를 자동으로 테스트·배포 가능한 상태로 유지하여, 필요한 시점에 운영 환경(Production)으로 안정적으로 배포할 수 있도록 하는 방식입니다.
- `CD (Continuous Deployment)`란 Continuous Delivery에서 한 단계 더 나아가, 자동화된 검증을 통과한 변경 사항을 별도의 수동 승인 없이 운영 환경까지 자동으로 배포하는 방식입니다.

## IaC
- `IaC(Infrastructure as Code)`는 서버, 네트워크, 스토리지 등의 인프라 구성을 코드나 설정 파일로 정의하고 관리하는 방식입니다.
- 기존에는 인프라를 수동으로 프로비저닝하고 변경했기 때문에 구성의 일관성과 재현성을 보장하기 어려웠으며, 인프라 규모가 커질수록 관리 부담과 설정 오류가 증가하는 문제가 있었습니다.
- 코드로 정의한 인프라 구성은 VCS(Version Control System)에 저장해 버전 관리하고, 변경 이력을 추적하며 팀과 공유·검토할 수 있습니다. 이를 통해 **인프라를 일관되고 반복 가능하게 구성하고, 변경 사항을 자동화하여 적용할 수 있습니다.**

## GitOps
- `GitOps`는 **Git과 같은 버전 관리 시스템에 선언적으로 정의된 원하는 상태(Desired State)와 실제 시스템 상태(Actual State)를 지속적으로 비교하고, 차이가 발생하면 자동으로 일치시키는 조정(Reconciliation) 과정을 통해 애플리케이션과 인프라를 관리하는 운영 방식**입니다.
- 기존에는 인프라와 애플리케이션의 구성을 수동으로 변경하거나 배포하는 과정에서 설정 불일치(Configuration Drift), 환경 간 구성 차이, 배포 실패 등의 문제가 발생했으며, 변경 이력 추적과 장애 복구에도 어려움이 있었습니다.
- GitOps를 사용하면 선언적 구성(Declarative Configuration)을 기반으로 시스템 상태를 자동으로 동기화하여 구성의 일관성을 유지하고, 변경 이력 추적과 이전 버전으로의 복원(Rollback), 원하는 상태로의 자동 복구(Self-healing)를 통해 운영 안정성을 높일 수 있습니다.
- 대표적인 GitOps 도구로는 Argo CD, Flux CD 등이 있습니다.

## Serverless
- `Serverless`는 서버가 없다는 의미가 아니라, **서버 인프라의 프로비저닝·운영·확장을 서비스 제공업체가 맡아 개발자는 애플리케이션 코드에 집중하도록 하는 클라우드 실행 모델**입니다. 서비스 제공 업체는 퍼블릭 클라우드 업체 또는 개발팀을 지원하는 사내 IT 부서일 수 있습니다.
- IaaS(Infrastructure as a Service)는 미리 정한 용량의 인프라를 할당받아 사용하기 때문에 실제 사용 여부와 관계없이 서버가 켜져 있는 동안 비용이 발생하지만, Serverless는 필요한 시점에만 서비스를 실행하고 클라우드 제공자가 자원을 자동으로 할당·확장하며 서버 관리를 맡아, 유휴 자원 비용과 운영 부담을 줄입니다.

## Service Discovery
- `Service Discovery`는 네트워크 내에서 실행 중인 서비스 인스턴스의 위치(IP 주소, 포트 등)를 자동으로 탐색하고 관리하여, 서비스 간 통신을 가능하게 하는 메커니즘입니다.
- Cloud Native 환경에서는 컨테이너의 동적인 생성·종료·재시작으로 IP 주소가 변경되어 서비스 간 통신이 어려울 수 있지만, Service Discovery를 사용하면 서비스 인스턴스의 위치를 자동으로 추적하고 제공하여 안정적인 통신을 지원할 수 있습니다.

## Service Mesh
- `Service Mesh`는 마이크로서비스 간 네트워크 통신을 관리하고, 트래픽 제어(Traffic Management), 관측 가능성(Observability), 보안(Security), 신뢰성(Reliability) 등의 기능을 일관되게 제공하는 인프라 계층입니다.
- 기존에는 서비스 간 통신에 필요한 트래픽 제어·암호화·모니터링 등의 기능을 각 애플리케이션에 직접 구현해야 했지만, Service Mesh를 사용하면 애플리케이션 코드 변경 없이 이러한 기능을 일관되게 제공하여 개발 및 운영 복잡성을 줄일 수 있습니다.
- Service Discovery는 동적으로 변경되는 서비스의 위치를 탐색하는 기술이고, Service Mesh는 서비스 간 통신을 제어하고 보안·관측 가능성·신뢰성을 제공하는 기술입니다

## k3s
- `k3s`란 Rancher Labs에서 개발한 오픈소스 경량 Kubernetes 배포판으로, 리소스가 제한된 Edge 환경, IoT 장치 및 소형 서버에 최적화되어 있습니다.
